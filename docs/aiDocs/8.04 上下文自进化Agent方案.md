## 0. 一句话结论

我们**已经拥有 context-centric 主路径**（不可变记忆快照 → ContextBuilder → Loop → commit_turn → 后台 Reviewer 回写 Hot/Daily）。真正缺的是：**把「下一 turn 会吃到的上下文」当成可演化资产来运营**——用 Generator / Reflector / Curator 式旁路，对 playbook（策略记忆）、procedural（Skill/workflow）、以及上下文装配策略做增量进化；**不改 `AgentLoop.run_turn` 签名，不把进化塞进主对话延迟路径**。

Skill/Tool 后续本质是 plugin：进化产物只要落到 `data/skills/`、`MEMORY.md`、或 ContextBuilder 可注入的新层，就会在下一 turn 自然生效。

## 1. 我们现在站在哪

### 1.1 已闭环的「事实 → 上下文」回路

```text
InboundEvent
  → MemoryManager.build_context → MemoryContextSnapshot（本 turn 不可变）
  → AgentLoop.run_turn / ContextBuilder.building_context
       [system | memory | skills L1 | ephemeral | history]
  → Tool 循环（含 memory_read / memory_edit）
  → SqliteSessionStore.commit_turn（transcript + review outbox 同事务）
  → on_turn_committed → ReviewerWorker → RuleBasedExtractor → Manager.apply
  → 下一 turn 的 snapshot 变化（进化的唯一可见效果面）
```

| 层 | 现状 | 对进化的意义 |
|----|------|----------------|
| Hot（USER/GROUP/MEMORY.md） | 默认注入；字符预算；`Manager.apply` 唯一写口 | **在线 playbook / 语义记忆**的落点 |
| Daily | 按日；默认不进 prompt | 事件日志；可被 curator 提炼进 Hot |
| Episodic（SQLite） | 完整轨迹；LIKE 检索 | Reflector 的原料；不可变审计 |
| Skills L1/L3 | Registry 扫描；摘要进 context | **程序性记忆**落点；进化写 `data/skills/` 即可 |
| Provider | 契约就绪；生产可空 | 外部长期记忆 / 向量召回 |
| Evolution 包 | 仅 docstring 骨架 | 本方案要填空的主战场 |

### 1.2 设计红线（必须延续）

来自 7.14 / 7.23，本方案不得违反：

1. **Loop 不写盘、不认识 Channel**；进化在 **persist 之后旁路**。
2. **本 turn 快照不可变**；本 turn 写入只影响下一 turn。
3. Agent/工具 **不得**直碰记忆文件路径或 SQL；变更经 `MemoryManager.apply`。
4. Evolution **不改 `run_turn` 签名**（7.14 E-20）。
5. 主回复路径不被 reviewer / curator / skill_creator 阻塞。

### 1.3 与「自进化」的差距（诚实定义）

当前 Background Reviewer = **记忆自维护**（规则抽偏好/约束/事件），还不是完整自进化。缺的是：

| 缺口 | 说明 |
|------|------|
| 策略级 playbook | MEMORY.md 无「可评分、可增量 delta」的策略条目结构 |
| 轨迹级 Reflector | 无独立 LLM 复盘「成功/失败战术」 |
| 程序性沉淀 | SkillCreator / Optimizer 空壳；AWM/Voyager 式 workflow 未做 |
| 上下文装配策略 | ContextBudget / Compactor / `sync_turn` 未接生产或未默认开启 |
| 安全门控 | 无 held-out / 回滚；裸写上下文有「越进化越差」风险 |
| Slice 15 | 环境快照；复现进化前后差异需要它，可后置 |

## 2. 业界做法速览（以上下文为学习介质）

共同范式：**不更新权重，演化注入模型的上下文**（memory / prompt / skill / workflow）。以下按「与我们贴合度」排序。

### 2.1 ACE — Agentic Context Engineering（ICLR 2026）

论文：*Agentic Context Engineering: Evolving Contexts for Self-Improving Language Models*（arXiv:2510.04618）。

| 角色 | 职责 |
|------|------|
| **Generator** | 用当前 playbook 解题，产出轨迹，并标注哪些 bullet 有用/误导 |
| **Reflector** | 对照执行反馈（可无人工标签），提炼可复用 insight |
| **Curator** | 把 insight 变成 **增量 delta**（ADD / UPDATE / REMOVE），确定性合并进 playbook |

关键创新：

- 反对 **brevity bias**（把策略压成空泛短句）与 **context collapse**（整篇重写越写越短、信息蒸发）。
- **Grow-and-refine**：局部增量 + 去重/修剪有害条目，而非 monolith rewrite。
- 同时覆盖 **offline**（优化 system prompt）与 **online**（运行时 memory）。

**对我们**：几乎可 1:1 映射——Generator ≈ 现有 AgentLoop；Reflector ≈ `evolution/reviewer`；Curator ≈ `memory_curator` + `Manager.apply` 增量 mutation；playbook ≈ 结构化后的 `MEMORY.md`（或独立 playbook 文档）。

### 2.2 Dynamic Cheatsheet（DC）

EACL 2026 / arXiv:2504.07952。黑盒模型在推理时维护一份**自策展小抄**（策略、代码片段、元启发），跨查询复用；无标签也可靠执行反馈学习。变体：Cumulative / Retrieval-Synthesis / Hybrid。

**风险**（RSEA 论文对照）：无门控的在线策展方差大，某些基准上会显著退化。

**对我们**：Hot MEMORY 的「精选可迁移片段」方向一致；必须加 **合并门控**，不能无脑 append。

### 2.3 Reflexion / Self-Refine

回合内或回合后用自然语言反思写入记忆，下一试次条件化。偏 **短环纠错**，不解决长期 playbook 组织与 collapse。

**对我们**：可作 Reflector 的轻量模式（单次 LLM 复盘 → 1–3 条 mutation），不要当作唯一架构。

### 2.4 Generative Agents / 分层记忆

观察 → 重要性评分 → 反思 → 检索注入。强调 **时间衰减 + 反思摘要**。

**对我们**：Daily + Episodic + Hot 分层已对齐；缺的是「反思层」调度与重要性启发式（可后置，用规则/LLM 评分）。

### 2.5 MemGPT / Letta — 分层分页

Core（常驻）/ Recall / Archival；模型用工具主动搬移记忆，把上下文窗口当 OS 内存。

**对我们**：`memory_read` / `memory_edit` + Hot 默认注入 ≈ Core；Episodic search ≈ Recall；Provider ≈ Archival。不必再造 OS 隐喻，补齐 **分页策略与预算接线**即可。

### 2.6 Voyager Skill Library + AWM Workflow Memory

| | Voyager | AWM |
|--|---------|-----|
| 沉淀物 | 可执行 skill（代码/技能库） | 高层 workflow recipe（3–6 步可泛化流程） |
| 使用方式 | 检索后调用/组合 | 检索后注入指导后续生成 |
| 在线性 | 终身增长 | offline / online 均可 |

**对我们**：`data/skills/*/SKILL.md` + `use_skill` = Voyager 面；AWM 的「recipe」可先写成 Skill 正文里的步骤清单，或 MEMORY 中的 procedural bullets——**不必新开第三套存储**，先统一进 Skill Registry。

### 2.7 RSEA — Held-Out Selection（可靠性关键）

*Recursive Self-Evolving Agents via Held-Out Selection*：多层自然语言状态（策略 / skills / playbook）演化后，**仅当 held-out 不回退才提交**；无门控的 DC 类方法会在部分任务上崩溃。

**对我们**：进化写入必须有 **候选 → 验证 → 提交/回滚**（哪怕第一版验证只是「字符预算合法 + 去重 + 人工/规则红线」），完整 held-out 可后置。

### 2.8 对照总表

| 范式 | 学什么 | 写入形态 | 我们的落点 |
|------|--------|----------|------------|
| ACE | 策略 playbook | 增量 delta bullets | Hot MEMORY + Curator |
| DC | 小抄片段 | 自策展 append/refine | Hot + 门控 |
| Reflexion | 失败教训 | 短反思文本 | Reviewer / Extractor |
| Generative Agents | 重要性反思 | 分层摘要 | Daily→Hot 提炼 |
| MemGPT | 分层驻留 | 工具搬移 | memory_* 工具 + Budget |
| Voyager | 可执行技能 | Skill 库 | `data/skills/` |
| AWM | 流程 recipe | workflow 记忆 | Skill 或 playbook section |
| RSEA | 可靠提交 | held-out gate | Evolution 提交协议 |

## 3. 目标架构：围绕 AgentLoop 的旁路进化

### 3.1 核心命题

> **自进化 = 改变下一 turn 的 Context 构成与质量。**  
> Loop 只负责「在给定上下文下把本 turn 跑完」；进化系统负责「让上下文随经验变好」。

### 3.2 目标数据流（不改 Loop 签名）

```text
                    ┌─────────────────────────────────────────┐
                    │           主路径（低延迟）                │
  Channel → Gateway → build_context → AgentLoop.run_turn      │
                    │         ↓ commit_turn                   │
                    │         ↓ OutboundReply                 │
                    └───────────────┬─────────────────────────┘
                                    │ on_turn_committed / EventBus
                                    ▼
                    ┌─────────────────────────────────────────┐
                    │     EvolutionScheduler（旁路，异步）       │
                    │  1. MemoryReviewer（已有：事实抽取）       │
                    │  2. EvolutionReflector（新：战术复盘）     │
                    │  3. PlaybookCurator（新：delta → apply）   │
                    │  4. SkillCreator/Optimizer（条件触发）     │
                    │  5. Compactor（预算/定时）                 │
                    └───────────────┬─────────────────────────┘
                                    │ MemoryMutation / SKILL.md
                                    ▼
                         下一 turn 的 ContextBuilder 输入变好
```

### 3.3 角色映射（ACE × DemoCursor）

| ACE | DemoCursor 组件 | 实现策略 |
|-----|-----------------|----------|
| Generator | `AgentLoop` + tools | **已有**；可选：轨迹上标注「引用了哪些 memory/skill 条目」（后置遥测） |
| Reflector | `evolution/reviewer.py`（填空） | 消费 `TurnEnvelope` + 可选 tool 成败信号；输出 `EvolutionInsight[]` |
| Curator | `evolution/memory_curator.py` + `Manager.apply` | insight → `MemoryMutation`（增量，禁止整文件 LLM 重写为首选） |
| Playbook | 结构化 `MEMORY.md` entries / 新 section `## Playbook` | 条目带稳定 id，支持 ADD/UPDATE/REMOVE |
| Skill 进化 | `skill_creator` / `skill_optimizer` | 写 `data/skills/`；Registry 热扫描或进程内 reload |
| Gate | 新：`EvolutionCommitGate` | 预算、去重、红线、可选回放评分 |

### 3.4 三种「上下文资产」（建议显式分层，避免一锅粥）

| 资产 | 存哪 | 进 Context 方式 | 谁写 |
|------|------|-----------------|------|
| **Semantic / Profile** | USER/GROUP.md | 默认 Hot | Reviewer（事实）+ 用户 memory_edit |
| **Strategy Playbook** | MEMORY.md 固定 section 或独立 playbook.md | 默认 Hot（受 2200 字预算） | Curator（增量 delta） |
| **Procedural** | `data/skills/*/SKILL.md` | L1 摘要；按需 L3 | SkillCreator / Optimizer |

Daily 仍作原料，不默认进 prompt（与 7.23 一致）。

## 4. 落地 Plan（按 Slice，可 TDD）

原则与 Memory 阶段相同：**每 Slice 可独立验收；只打公共 seam；进化不阻塞主路径。**

### Phase 0 — 接线与观测（0.5–1 天）· 进化地基

**目标**：让旁路「看得见、接得上」，仍不改 Loop 语义。

| 项 | 动作 |
|----|------|
| P0.1 | Gateway 生产路径传入 `context_budget`（能力已在 Loop/Builder，默认未开） |
| P0.2 | `commit_turn` 后调用 `MemoryManager.sync_turn`（已实现未接线） |
| P0.3 | `EvolutionScheduler` 最小实现：挂在 `on_turn_committed` 之后扇出（先只 fan-out 到现有 ReviewerWorker，接口预留 Reflector） |
| P0.4 | EventBus 订阅 `turn_end` / `tool_*`：落一条轻量 `evolution_signals`（成功/失败/迭代次数），供 Reflector 用不二次扫全库 |

**验收**：主对话延迟不明显增加；关闭 evolution 开关行为与今日一致；ContextBudget 超限路径可测。

---

### Phase 1 — Playbook 增量策展（2–3 天）· ACE 最小闭环

**目标**：MEMORY 从「散文日记」变成「可 delta 的策略条目」，完成 Generator→Reflector→Curator 在线环。

| 项 | 动作 |
|----|------|
| P1.1 | 约定 playbook entry 格式（与现有 Hot entry 围栏兼容）：稳定 `id`、`helpful/harmful` 计数可选、正文短策略 |
| P1.2 | `EvolutionReflector`：输入 `TurnEnvelope` + signals → `EvolutionInsight`（含建议 op） |
| P1.3 | `PlaybookCurator`：insight → `MemoryMutation`；**禁止**默认整文件 rewrite；走 `Manager.apply` |
| P1.4 | `EvolutionCommitGate` v0：超预算拒绝 / 近重复拒绝 / 空 insight 跳过；失败写审计不抛主路径 |
| P1.5 | 替换或并联 Extractor：事实类仍 `RuleBasedExtractor`；策略类走 Reflector（职责分离，对齐 ACE「Reflector 与 Curator 分家」） |

**验收**：

- 人为构造「同一类失败」多 turn 后，MEMORY playbook 出现对应避坑条目，且下一 turn snapshot 含该条目。
- 强制 curator 做 monolith 重写的对照实验应**不允许**进入默认路径（防 collapse）。
- 现有 Memory 125 tests 不回归；新增 seam 测试不 mock Manager。

**明确不做**：Skill 自动创建、held-out 基准、offline 优化 systemPrompt。

---

### Phase 2 — Compactor 与防 Collapse（1–2 天）

**目标**：playbook 只增不减会胀死；用 grow-and-refine 而非「总结成三句话」。

| 项 | 动作 |
|----|------|
| P2.1 | 注入默认 `Compactor`：合并重复、降权长期 harmful、归档到 Daily/备份，保持 Hot ≤ 预算 |
| P2.2 | Curator 统计：entry 被引用/关联失败时的加权（可先规则：连续 N 次同类失败未改善 → 标记） |
| P2.3 | 定时/阈值触发：`EvolutionScheduler` cron 或每 N turn / session_end |

**验收**：MEMORY 在 50+ turn 模拟后仍 ≤ 字符上限；关键策略条目不被「摘要掉」；budget_exceeded 在有 Compactor 时转为整理而非硬失败（与 7.23 seam 一致）。

---

### Phase 3 — 程序性进化（Skill 作为 plugin 产物）（2–3 天）

**目标**：复杂可复用轨迹 → Skill；失败 Skill → 修正。对应 7.12 阶段 6 自测意图，但存储统一到现有 Skill 体系。

| 项 | 动作 |
|----|------|
| P3.1 | `SkillCreator`：Reflector 判定「可复用多步流程」→ 生成 `data/skills/<slug>/SKILL.md`（AWM recipe 风格：目标、前置、步骤、失败处理） |
| P3.2 | Registry reload 或启动扫描；L1 摘要自动进下一 turn context |
| P3.3 | `SkillOptimizer`：`use_skill` 后 tool/轨迹失败信号 → patch SKILL.md（小 diff，保留版本备份） |
| P3.4 | Gate：新 Skill 默认 `draft`；连续成功 M 次或人工确认后 `active`（防污染 L1 摘要槽位） |

**验收**（对齐 7.12 阶段 6 精神，指标可调）：

- 重复相似任务达到阈值阈值后出现新 Skill 文件。
- 故意破坏 Skill 步骤后，optimizer 能生成修正版且旧版可回滚。
- **不**把 procedural 再做成与 `skills/` 平行的第二套 `memory/procedural` 生产路径（骨架可删或标 deprecated，避免双轨）。

---

### Phase 4 — 装配策略进化（可选，1–2 天）

**目标**：进化「什么进 context」，而不只是「文件里有什么」。

| 项 | 动作 |
|----|------|
| P4.1 | `include_today_daily` / Provider recall / Skill 摘要裁剪策略可配置；记录每次 turn 的装配选择 |
| P4.2 | 补齐 ContextBudget 第 4 步「缩短 Skill 摘要」（7.23 §17 缺口） |
| P4.3 | Offline ACE：用一批固定任务离线优化 `systemPrompt.md` 或 playbook 初始种子（低优先级） |

---

### Phase 5 — 可靠性与复现（后置）

| 项 | 动作 |
|----|------|
| P5.1 | RSEA 风格 held-out：小固定任务集，候选 playbook 回放不降级才 commit |
| P5.2 | Slice 15 环境快照：模型版本、prompt hash、工具 schema、skill 版本 — 对比进化前后 |
| P5.3 | 进化审计表：谁在何时对哪条 entry 做了何种 delta |

## 6. 推荐实施顺序（执行视图）

```text
Phase 0 接线观测
    → Phase 1 ACE 在线 playbook（最大杠杆）
        → Phase 2 Compactor / 防 collapse
            → Phase 3 Skill 作为程序性 plugin 产物
                → Phase 4 装配策略（可选）
                    → Phase 5 held-out + Slice 15（可靠与科研向）
```

**为什么 Playbook 先于 Skill**：你们已有 Hot 注入与 `Manager.apply`；策略条目立刻改变每一 turn 的默认 context，ROI 最高。Skill 是 plugin 面，等 Reflector 能稳定识别「可复用流程」再写盘，避免垃圾 Skill 占满 L1 摘要。

**为什么 Tool 不是主线**：Calculator / memory_* / use_skill 协议已通；file/bash 等属于能力 plugin，与「上下文自进化」正交，可并行但不阻塞本 plan。

## 7. 风险与对策

| 风险 | 来源 | 对策 |
|------|------|------|
| Context collapse | 整篇 LLM 重写 MEMORY | 默认只允许增量 delta；Compactor 做结构化合并 |
| Brevity bias | 「总结成三条原则」 | Playbook 保留具体战术/反例；预算内偏详不偏空 |
| 越进化越差 | DC 无门控 | CommitGate；draft Skill；后续 held-out |
| 主路径变慢 | 同步 LLM 复盘 | Scheduler 异步；与 ReviewerWorker 同模型队列可限流 |
| 双轨存储 | procedural/ vs skills/ | 生产只认 skills/；procedural 标遗留 |
| 污染用户画像 | 策略写进 USER.md | 策略只进 MEMORY playbook section；画像仍走事实 Extractor |
| 测试假绿 | mock 掉 Manager | 延续 7.23 TDD 纪律：经真实 apply/read 断言 |

## 9. 成功标准（产品级）

1. **可见进化**：同一用户连续使用后，无需用户手动 `memory_edit`，Hot playbook 出现可指认的避坑/偏好策略，且可在 transcript 审计中追溯来源 turn。  
2. **主路径稳定**：开启进化后 P50 回复延迟增幅可控（异步）；关闭开关可完全回退。  
3. **无 collapse**：长程运行 Hot 体积受控，且关键条目存活（抽检）。  
4. **Plugin 闭环**：至少 1 条自动生成的 Skill 能被 L1 展示并被 `use_skill` 成功执行。  
5. **契约兼容**：不破坏 7.14 Loop 边界与 7.23 Memory seam；Memory 回归测试全绿。
