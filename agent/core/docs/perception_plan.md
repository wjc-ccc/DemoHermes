## 优化perception架构 


**什么有资格进入上下文；什么信息应该被压缩、排序或者丢弃；什么信息必须在模型推理之前就必须结构化出来**


### 1. **上下文分诊**：重点去做上下文分级 上下文的逻辑优化 （最高优先级）--- lost in the middle

把所有候选 context 信息分成 P0/P1/P2/P3 四级，从高到低塞，塞到 token 预算耗尽。

#### P0 P1：重点是识别不同任务的不同重点信息（常规的系统提示词 + 用户个人当前请求）

P0/P1 信息是下一步推理必须依赖的材料，要保证模型可以稳定看到。比如
**代码任务里的当前用户需求、失败测试、错误堆栈、待修改文件、核心接口定义；**
**客服任务里的订单状态、当前生效规则、用户当前问题；**
**数据分析任务里的目标指标、字段定义、查询结果摘要。**


#### P2；重点是压缩为anchor + 按类型merge

P2 信息通常有价值，但不一定需要原文全部进入 context。比如较早的对话历史、背景文档、旧工具结果、相关但非核心的代码文件、长日志中的趋势信息。它们能帮助模型理解背景，但如果原样放进来，会占掉大量 token，还可能把 P0 信息挤远。所以 P2 的处理方式不是丢掉，而是压缩后进入。语义压缩我们下一个模式还要细聊，这里我们先把握大致思路。

**anchor 包含 intent、changes、nextstep、excluded、decision**


#### P3：重点是挂handle 和指标计算（比如 p3 hit_rate）

P3 信息并不是完全没用，但现在不值得占用上下文窗口。比如整个代码仓库、全量日志、完整知识库、历史工单全集、所有 PDF 原文、所有数据库表结构。它们里面可能藏着答案，但在当前这一步推理里，还没有足够理由把它们展开。对 P3，正确做法是挂 handle：

repo://src/auth/*
log://payment/last_24h
doc://refund-policy/archive
table://orders/schema
file://design/login-flow.pdf



### 2. 个人代码/日常生活助手  上下文逻辑设定

对于不同优先级 默认加载文件 都是用原子item类别转入 加载进来 然后按照 优先级组装  方便trace和按照逻辑压缩（anchor + 占位符）

P0 （总是加载 5-10%）:静态系统提示词（system prompt + skill/tool的介绍 + 安全规则（需要管理员系统）） + 动态系统提示词（当前工作区状态/user id/任务 最近的user query 等等） --- trace追踪

P1（有空间再加载 20-30%预算）：修改过的文件/最近的工具执行结果/错误信息 （当前步骤执行的逻辑） 

P2（压缩摘要，10-20%预算）：messages 包含近几轮对话内容（这部分也是压缩的主体 按照特定结构化压缩后 可能是anchor1+messags[0:first_anchor]后续merge形式压缩）   anchor 保留 intent  change  excluded  next_step 

P3：lazy load 只给出索引链接 or 提供获取工具 

**每一部分都应该有自己的预算 和 统计指标（p99//hit_p3_rate）**

### 3. 语义压缩优化：自动压缩阈值 + anchor类型压缩（某一段对话压缩为结构化语句 包含 用户要什么 改了什么 调用了什么 做了哪些判断 下一步做什么 排除了什么 + 按照五大问题分别merge合并之前压缩片段） + 不同历史消息不同压缩方式（因此对于agent行动需要分类 observation可以占位符 动作就需要Summarization 简单问题不需要压缩 or 只保留最近几轮）

**重点针对于P2类型信息**

对于不同优先级信息 统一底层 content 包含字段

- 自动：必须自动化，否则长 session 迟早撞墙（师承 Claude Code）。
- 演化：不要每次重写历史，而要维护持续演化的 anchor（师承 Factory）。
- 分治：不能只有一种算法，而要根据 Action、Observation、Error、Decision 的不同性质分层处理（师承 OpenHands）。



### 3. 观察逻辑压缩（Observation Masking） 和 anchor压缩共同使用 or 按优先级划分？ 或者按照任务类型划分？

核心做法：将工具调用返回的大量输出内容（如读取的文件全文、Shell命令结果、API响应等）替换成一个简短的占位标记，例如 [这里曾经有工具输出，如需查看请检索]。
在具体实现中，Observation Masking通常遵循一个简单的逻辑：将完整输出存入外部存储，分配唯一ID，然后在上下文中替换为 [Obs:{ref_id} elided] 这样的模板。

为什么这招管用？
因为在Agent的轨迹中，工具输出往往是最"膨胀"的部分——实测数据显示，工具输出通常占上下文的70%以上，而真正需要在后续步骤中参考的往往只是其中很小的一部分。

Deep Agents的两种卸载策略：

卸载类型	触发时机	内容	阈值
大工具结果卸载	每次工具调用后	大工具响应内容	>20,000 tokens
大工具输入卸载	上下文超阈值时	旧的写入/编辑参数	上下文85%阈值
示例：

原始：
├─ User: 读取 /src/config.py
├─ Assistant: [调用 read_file]
└─ Tool: [3000行代码内容]

卸载后：
├─ User: 读取 /src/config.py
├─ Assistant: [调用 read_file]
└─ Tool: [文件已保存至 /memory/obs_123.txt，前10行预览: ...]



#### 其他harness参考（自动压缩+anchor+细分llm的历史消息 然后特定逻辑处理）

- Claude 内置auto compaction：上下文接近上限时就自动压缩旧内容
  - **风险不只是装不下，还有多了推理质量也会下降**

- Factory：压完之后历史怎么持续演化，普通压缩容易像复印件反复复印丢失细节
  - 维护一个持续更新的anchor，每次有新对话、新改动、新工具结果，都要把新信息合并进已有 anchor（摘要二来源于摘要一后agent的轨迹 但是摘要二不是append 而是逐条接到一的每部分后边）
  - anchor 至少要保住几类信息：**Intent：用户要什么。Changes made：已经改了什么、调用了什么。Decisions taken：已经做了哪些判断。Next steps：下一步做什么。Excluded_approaches，已经排除的方案。**不需要记住每一屏输出，但必须记住自己走过哪些路。

普通：摘要 -> 摘要的摘要 -> 摘要的摘要的摘要 （越来越模糊）
anchor：摘要0-> 摘要1-> 摘要2  （anchor仍然清晰）

- openhands：可配置的压缩器（不压/保留最近/llm/masking/渐近遗忘）
  - agent历史消息中 包含 action 和 observation，action是agent做过什么 observation是外部世界的返回，很多observation不需要保留。探索agent，可以换成占位符（observation masking），但是如果更多是动作和结论（llm Summarization）。简单问题 可以不压缩/只保留最近几轮

### 参考trace逻辑 

分诊压力：每次请求占用多少上下文预算 有多少信息被丢失或延后
  - 平均值不够，要看 p95、p99。平均请求正常，不代表长尾请求正常。如果 p99 的 dropped_count 突然升高，说明某类任务的信息量已经压垮了当前分诊策略。
关键层丢失：P2/P3延后正常 但是P0/P1信息不应该丢失，P0丢是bug，P1/2丢说明预算太紧了
P3回取率：P3的价值是让agent能去回来 如果实际取/暴露的高 那么说明降级到P3太狠了



Perception Trace 要记录的不是模型最后说了什么，而是模型在开始推理之前经历了什么：读了哪些文件检索到了哪些内容选中了哪些片段丢弃了哪些材料压缩了哪些历史调用了哪些发现动作关键证据最终落在上下文什么位置如果用户问：订单为什么不能退款？而最终答案错了。这时候普通日志只能看到：answer = "该订单已超过退款期限"而 Perception Trace 能告诉你：检索命中：47 条进入 context：6 条被丢弃：41 条关键证据：refund_policy_v3.md→ 被排序到第 38 位→ 未进入 context实际进入：refund_policy_v1.md此时核心问题就会暴露的比较清晰。上下文分诊、语义压缩、渐进发现和多模态融合四个模式都在做不同的信息处理动作。但它们最终都会留下同一种痕迹，就是信息从哪里来、为什么进来、为什么被压缩、为什么被丢弃，以及为什么被重新取回。
